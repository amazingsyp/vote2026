# qa-and-deploy — 통합 검증·배포

산출물이 실제로 맞물려 동작하는지 검증하고, 통과하면 GitHub Pages로 배포한다.

## 왜 이렇게 하나
경계면(데이터 shape ↔ 프론트 소비)에서 버그가 가장 많이 난다. 파일 존재 확인이 아니라 **양쪽을 동시에 읽고 교차 비교**해야 undefined·필드 불일치를 잡는다. 로직은 실제 입력으로 돌려봐야 맞는지 안다.

## 1) 경계면 교차 비교
`index.html`(또는 04_frontend_notes의 소비 필드 목록) ↔ `*.json` 실제 필드를 표로 대조:
- 프론트가 읽는 키가 데이터에 존재하는가
- 타입·중첩 구조 일치(예: `pledges[].title`)
- id·선거구 코드가 candidates와 districts에서 동일 체계인가
불일치는 필드명·위치와 함께 책임 에이전트에 수정 요청.

## 2) 로직 실행 검증
- **채점**: 전부 매우동의/전부 매우반대/전부 중립/혼합 응답 → 각 축이 ±100·0에 닿는지(quiz report 검산표와 대조).
- **매칭**: u==c → 100%, 정반대 극단 → 0% 근처, 무작위 → 0~100 범위. 단조성(가까울수록 높음) 확인.
- **주소→선거구**: 샘플 주소 3~5개 → 기대 선거구·후보 노출.

## 3) 헤드리스 동작 (가능 시)
webapp-testing(Playwright)로 로컬 서빙 후: 설문 완주 → 성향 레이더 → 주소 입력 → 후보 결과까지 흐름과 **콘솔 에러 0**을 확인. 스크린샷 1~2장 첨부.

## 4) 알려진 한계 vs 버그 구분
의원 선거구 미해결, 사진 없는 후보, 무소속 중도 점수 등은 한계로 분류. 데이터-프론트 불일치·로직 오류만 버그.

## 5) 배포 (GitHub Pages)
검증 통과 후에만:
1. git 저장소 초기화/원격 확인(없으면 `gh repo create` 제안).
2. `index.html`(+`data.json`) 커밋·push.
3. Pages 활성화(`gh api`로 source=main 루트 설정) 또는 사용자 안내.
4. 배포 URL 확인·보고. **사용자 승인 없이는 push·공개하지 않는다**(외부 공개 행위).

## 산출
`_workspace/05_qa_report.md`: 경계면 대조표, 로직 검증 결과, 버그+심각도, 한계 목록, 배포 URL.

## 흔한 함정
- "파일 있음 = 통과"로 끝내기 — 반드시 필드 교차 비교.
- 빈 데이터로만 테스트 — 실제 후보 레코드로 검증.
- 검증 전 배포 — 금지. 통과 후 사용자 승인받고 배포.
